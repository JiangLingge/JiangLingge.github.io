Hexo 博客部署到 GitHub Pages：自定义域名与 HTTPS 全流程

发表于2026-10-08|更新于2026-10-08|技术笔记
|总字数:1.4k|阅读时长:4分钟

文章在本地写得再顺，不推上去也只是个本地文件夹。这篇记录把 Hexo 博客发布到 GitHub Pages 的完整流程，以及怎么绑定自己的域名。

零、前置检查：本机有 Git 吗

这一步最容易被跳过，但没有 Git 就根本发布不了：hexo-deployer-git 内部是直接 spawn('git', ...) 调用命令行的，不是纯 JS 实现。

如果提示「不是内部或外部命令」，先去 git-scm.com 装，或者：

一、先选仓库类型

GitHub Pages 有两种站点，选错了路径会全乱：

类型 仓库名 访问地址
用户站点 <用户名>.github.io https://<用户名>.github.io
项目站点 任意名字，如 blog https://<用户名>.github.io/blog

执行 hexo d 时会提示输入 GitHub 用户名和密码 —— 密码这里不能用登录密码，GitHub 早就禁掉了。要用 Personal Access Token：

  1. GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
  2. 生成一个勾了 repo 权限的 token
  3. 提示输入密码时粘贴这个 token

四、开启 Pages

推成功后去仓库 Settings → Pages，把 Source 设为 Deploy from a branch，分支选 main、目录选 / (root)，保存。

等一两分钟访问 https://<用户名>.github.io 就能看到博客了。没生效先看 Actions/Pages 的构建状态，别急着怀疑配置。

五、绑定自定义域名

1. 加 CNAME 文件

在源目录（不是 public/）建 source/CNAME，内容只有一行域名：

这个文件会随 hexo generate 一起进 public/，再从 public/ 推到 GitHub。不放在 source/ 里的话，每次部署都会被覆盖掉，绑定会莫名失效。

2. 配置 DNS 解析

去域名服务商添加记录。根域名（example.com）只能用 A 记录，指向 GitHub Pages 的四个 IP：

类型 主机记录 记录值
A @ 185.199.108.153
A @ 185.199.109.153
A @ 185.199.110.153
A @ 185.199.111.153

子域名（blog.example.com）用 CNAME：

类型 主机记录 记录值
CNAME blog <用户名>.github.io

CNAME 的值填 <用户名>.github.io，不要填仓库地址，也不要带路径。

3. 在仓库里填域名

仓库 Settings → Pages → Custom domain 填上域名并保存，它会自动帮你生成/校验 CNAME。下一步再勾 Enforce HTTPS。

4. 等解析生效

DNS 传播从几分钟到几小时都正常。用命令确认解析对不对：

解析到了正确的 IP 再访问域名，否则会看到 404 或者 GitHub 的默认页。

六、开启 HTTPS

域名验证通过后，Pages 设置页的 Enforce HTTPS 就可以勾了。GitHub 会自动签发 Let’s Encrypt 证书，一般几分钟内生效。

如果勾选框是灰的，常见原因：

  • DNS 还没生效，GitHub 校验不到域名
  • 之前刚解绑过域名，需要等一会儿再试
  • 域名用了不支持的 CNAME 层级（比如多层嵌套）

七、常见坑速查

现象 原因
页面打开是 404 分支名写错；或 Pages 还没构建完
样式和图片全丢 项目站点没配 root: /blog
推送成功但页面没变 推到了别的分支；或浏览器缓存，试试强制刷新
绑定域名过几天失效 CNAME 文件没放 source/ 目录
提示密码错误 用了登录密码，应该用 Personal Access Token
域名能访问但提示不安全 Enforce HTTPS 没勾，或证书还没签发完
RSS 里的链接是 localhost _config.yml 的 url 没改

八、不想折腾 GitHub Pages 的话

Vercel / Netlify 更省事：把源仓库（不是 public/）推到 GitHub，导入平台后设置构建命令 npx hexo generate、输出目录 public。之后每次 git push 自动重新构建，还能自动配好 HTTPS 和 CDN。

缺点是国内访问速度一般，要不要用看你的读者在哪。

最后

部署这一步看着步骤多，其实真正容易出问题的就三个地方：url 写对、分支写对、CNAME 放对位置。这三处确认了，剩下的都是等待时间的问题。
